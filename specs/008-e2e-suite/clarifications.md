## Q1: Which dataset?

- (a) TPC-H, generated by DuckDB's `dbgen`.
- (b) A public download — NYC taxi parquet, a Kaggle retail set.
- (c) A bespoke generator written here.
- **Chosen:** (a) — decided by the agent from measurements taken at clarify time. It generates
  locally in 0.18s at sf=0.01 and 9.5s at sf=1, needs no credentials, is byte-for-byte
  deterministic, and carries a scale knob so the same suite serves CI and a local soak run.
  Its dates span 1992–1998, which is the first corpus in this repo deep enough to test a
  yearly grain. (b) fails the repo's rule that fork PRs run without secrets, and puts a
  download on every run. (c) would cover the edge semantics better but proves nothing about
  behaviour on a recognisable, externally defined schema — and a generator written by the same
  hand as the engine is a weaker oracle.

## Q2: What is the oracle at 60,000 rows?

- (a) Pin every expected figure, computed once and pasted in.
- (b) Write the equivalent physical SQL by hand per case and compare results.
- **Chosen:** (b), with (a) for a handful of stable totals — decided by the agent from what
  each actually proves. A pasted figure at this scale is a number someone read out of the
  engine's own output, which makes it a regression test against *changing*, not a correctness
  test. Hand-written physical SQL is an independent statement of the same question, so a
  mistranslation fails even the first time it is run. That is what this engine's whole job is:
  turning a semantic request into physical SQL, so checking it against physical SQL written by
  a human is testing exactly the thing.

## Q3: Do the end-to-end tests run by default?

- (a) Opt-in only, deselected from the default run.
- (b) On by default at the small scale, with a marker so they can be deselected or scaled.
- **Chosen:** (b) — decided by the agent from the cost and from what happens to opt-in
  suites. At sf=0.01 the whole thing costs well under a second, so there is no reason to hide
  it; and a suite that only runs when someone remembers is a suite that rots. The marker exists
  so a contributor can run `-m "not e2e"` while iterating, and raise the scale factor when
  they want a soak run.

## Q4: What happens on a machine with no network the first time?

- (a) Fail.
- (b) Skip the suite with a reason.
- **Chosen:** (b) — decided by the agent from the README's own promise. The project's pitch is
  a clone that runs with "no database, no credentials and no network", and the extension that
  generates TPC-H is fetched once from DuckDB's repository. Failing the verify gate on a plane
  would make that promise false. Skipping keeps it true and keeps the unit tests — which
  really do need nothing — as the guarantee.

## Q5: How are nulls and booleans covered, given TPC-H has neither?

- (a) Accept the gap.
- (b) Build a second, small table in the same database, written for the edge cases.
- **Chosen:** (b) — decided by the agent from a probe: the denormalised TPC-H view contains
  zero nulls and no boolean column, so it cannot exercise `count` versus `count_distinct` on
  nulls, `<>` dropping null rows, boolean dimension typing, or the metric divisor guard. Those
  are precisely the traps the documentation warns about, so leaving them to the ten-row corpus
  would mean the large suite tests the easy half. The companion table is tiny and lives in the
  same fixture, so there is one setup path rather than two.

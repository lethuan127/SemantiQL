**T2.** `engine/validate.py` is the query-validation layer, which the constitution names a
trust-boundary artifact.

# What

`ORDER BY DATE_TRUNC('month', pickup_datetime)` sorts a monthly report, when the request selects that
same grain. And every ORDER BY refusal names what you *can* order by.

**Today the first is refused and the second is silent:**

```
> SELECT revenue, DATE_TRUNC('month', pickup_datetime) FROM trips
    ORDER BY DATE_TRUNC('month', pickup_datetime)
refused: ORDER BY takes the name of something this request selects, and a function is not one.

> SELECT revenue, DATE_TRUNC('month', pickup_datetime) FROM trips ORDER BY pickup_datetime_month
revenue   pickup_datetime_month
0.0       2002-12-01 00:00:00
```

The capability exists. The alias `pickup_datetime_month` is generated by the compiler and orders
correctly. Nothing tells the caller it exists.[^validate]

# Why

Observed, not imagined. A Claude building a model over **2.96 million real NYC taxi trips** hit this,
read the refusal, and reported to the analyst that monthly reports *"come back unsorted — sort them
yourself"*.[^observed] It was wrong, and the refusal is why: the message says what is not allowed and
never says what is, so the only inference available was that the feature is missing.

That is a direct failure of the reason this project carries refusals as ordinary answers. `AGENTS.md`
puts it plainly: a refusal must keep travelling with its reason "because that reason is what lets
Claude repair its own query". A refusal that cannot be repaired from its own text has the shape of a
help message and the effect of a dead end — and the user gets a worse answer while everything looks
like it is working.[^constitution]

Two other things make this worth more than a message tweak:

- **The other two branches already do it right.** Ordering by a position lists the orderable names;
  ordering by an unselected name runs `_suggest`. Only the function branch is silent, so this is an
  inconsistency inside one function rather than a missing feature.[^validate]
- **The refused query is the one a SQL author would write.** Repeating the select-list expression in
  ORDER BY is ordinary SQL. Refusing it teaches the caller that the grain is second-class, which then
  costs a round trip on every monthly report — or, as observed, is not recovered from at all.

# User stories

- **As Claude writing a monthly report**, I order by the grain I selected and it works — so I do not
  have to discover a generated alias to sort a series by time.
- **As Claude that has been refused**, the message tells me which names I may order by — so I repair
  the query instead of concluding the capability is absent.
- **As an analyst**, a month series arrives in month order.

# Functional requirements

- **FR-1** — `ORDER BY DATE_TRUNC('<grain>', <dimension>)` is accepted when the request selects that
  **same dimension at that same grain**, and orders by the corresponding output column.
- **FR-2** — It is refused when the request selects that dimension at a **different** grain, naming
  the grain that is selected. Ordering by a month the reader cannot see is the existing rule, not a
  new one.
- **FR-3** — It is refused when the request does not select that dimension at all.
- **FR-4** — `ASC`/`DESC` and `NULLS FIRST`/`NULLS LAST` work on the expression form exactly as on
  the alias form.
- **FR-5** — Every ORDER BY refusal names the orderable names. No branch is silent.
- **FR-6** — Ordering by any other function — `SUM(x)`, `UPPER(channel)`, `EXTRACT` — stays refused,
  and now says what may be ordered by instead.
- **FR-7** — The alias form keeps working. It is what every existing caller uses.

# Non-functional requirements

- **N1 / N2** — nothing here widens what reaches the database. An accepted ORDER BY resolves to an
  output column the request already projects, which is the same `OrderKey` the alias form produces,
  so `compile.py` is untouched and emits what it emitted before.[^constitution]
- **Trust boundary** — `engine/validate.py`. Called out, not routine.[^constitution]
- **The allowlist rule** — no new node type is consumed and no new SQL is emitted, so
  `_SELECT_ARGS`/`_FROM_NODE_ARGS` do not change. The constitution's rule is that the allowlist grows
  in the same change that teaches the compiler a construct; here the compiler learns nothing new.
- **Refusal-path tests** — a behaviour change in `validate` needs its refusals tested, including that
  the database is never reached.[^constitution]

# Out of scope

- **`ORDER BY` on an expression the request does not select.** Still refused; FR-2 and FR-3 keep that.
- **`HAVING`, and ordering by an aggregate.** Unchanged and still refused.
- **Sorting semantics** — nulls, collation, stability. Whatever Postgres and DuckDB already do.
- **The other finding from the same run**: that a model can be pointed at a database view carrying a
  `CASE` label column. That worked, and it is documented behaviour rather than a change.
